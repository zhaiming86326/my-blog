# coding-with-ai：AI 编码助手工作流指南

> 来源: [UDEL](https://lem.che.udel.edu/git/furst/coding-with-ai) · 由本地 LLM 概括（含全部 7 个章节）

## 概述

本文档是关于使用AI编码助手的工作流指南，涵盖了从选择合适的工具到如何有效利用这些工具的各个方面。文章详细介绍了不同类型的AI辅助工具（如聊天界面、代码补全、代理工具等）以及它们在实际编码工作中的应用。

## 两世界

### 关键思想
大多数人在遇到AI协助时都是通过浏览器窗口或独立的应用程序进行交互，即所谓的“web chat”。然而，这种模式并不适合编写代码。本文档旨在帮助读者从使用web chat的习惯中解脱出来，转向那些能够与你的代码文件直接互动的工具。

有两个世界值得区分：

1. **Web chat**：一个浏览器标签页或独立应用。AI对你的项目没有任何意识。
2. **在编辑器或终端内**：AI生活在你的代码所在的地方。它可以读取你的文件、修改它们，并且通常可以运行命令。

第一个适合解释、解释和有时规划，而第二个是实际编写代码时应该使用的工具。

### 关键目标
- 区分web chat与那些能够直接与你的代码互动的工具。
- 识别世界2中的光谱：自动补全、项目内聊天以及代理工作。
- 停止将浏览器标签页作为默认编码工作空间。

## 世界1：Web chat

一种基于浏览器或独立应用的模型对话。你输入内容，模型响应也在同一窗口中显示。

**示例（2026年初）**：ChatGPT、Claude.ai、Gemini、Microsoft Copilot（网页版）。每个都有免费和付费计划，并且可以通过大学或雇主协议获得机构访问权限。也可以自己托管一个聊天界面来使用本地模型。详见第7节。

**优点**：
- 一击即中解释：解释这个错误，这段日志是什么意思，这个正则表达式匹配什么
- 多轮设计讨论：我正在选择方法A和B，我想知道应该考虑哪些方面？
- 非代码工作：撰写文档、编写提交信息、解释概念

**缺点**：
- 与项目断开连接。模型是无状态的，并不知道你的文件存在哪些内容或你最近做了什么修改。
- 往返摩擦：你需要从终端复制，粘贴到聊天窗口中等待，阅读结果后再次复制并粘回编辑器。对于一击即中的任务来说还好，但对于迭代编辑则非常痛苦。
- 每次都需要记得带上相关上下文。

**陷阱**：因为web chat是大多数人学习的第一个界面，它就成为了他们的默认工具。如果你在一个会话中多次在浏览器标签页和你的编辑器之间复制粘贴代码超过几次，你就是在使用错误的工具。

## 世界2：与代码同居的AI

一个可以在你的编辑器或终端内看到文件并直接修改它们的AI助手。界面可能是侧边栏聊天、命令行输入、自动补全或者这些方式的组合，但共同点是这个工具“生活在代码所在的地方”。

**示例（2026年初）**：Claude Code（CLI, VS Code, JetBrains）、Cursor、Windsurf、GitHub Copilot、Cline、Aider、Microsoft Copilot代理模式。大多数现代工具结合了多种交互模式。

### 世界2中的光谱

一个与代码同居的工具可以以三种不同的方式操作：

1. **自动补全**：在你输入时提供下一行的预测文本。你可以保持完全控制，模型只是预测接下来的内容。便宜、快速且容易忽略错误。详见第3节。
2. **项目内聊天**：一个侧边栏或终端会话，在这里你可以进行对话并意识到你的文件。你可以询问设计问题、请求有针对性的更改或者在不离开编辑器的情况下让AI解释一些东西。如果你正在使用Claude Code在VS Code面板中操作，这就是你在做的事情。详见第4节。
3. **代理工作**：你给AI一个多步骤的目标，例如“找到X定义的位置并更新所有调用者，然后运行测试”，它会通过读取文件、进行更改、运行测试、阅读输出并逐步修复来执行这个循环。你设定目标，但代理执行步骤。详见第5节。

（2）和（3）之间的界限是模糊的，并且这是可以接受的。与项目内AI的对话在你要求它做多步任务时就变成了代理工作。它们不是两个不同的工具，而是同一个工具的不同操作方式。问自己的问题不应是“我在哪种模式下？”而应是“我现在要请求什么？”

### 历史注记：嵌入式编辑

2023-2024年的Copilot/Cursor时代中，第四种模式是**嵌入式编辑**：高亮一个代码块，按下热键（Cursor中的Cmd+K或VS Code中的“Edit with Copilot”），输入指令如“使其异步”或“添加错误处理”，然后会出现一个差异视图。没有对话，也没有代理循环，只有一次选择、一条指令和一个差异。

嵌入式编辑在2023年与指令调优的LLM（ChatGPT, GPT-4）一起出现，这些模型首次能够可靠地将自然语言指令转化为相应的代码转换。它们处于早期仅完成模式的时代（由Codex等驱动，并且没有代理循环）。随着工具变得更具代理性，这种模式已经淡出。你可以通过在项目内聊天中请求“将我高亮的函数改为异步”来实现同样的效果。新手用户可能完全跳过嵌入式编辑热键。我们提到它是为了让你能够识别旧教程描述的内容，而不是作为你需要从头开始学习的工作流。

### 如何选择

两个问题几乎涵盖了所有情况：

1. **答案是文字还是代码？**
   - 如果答案是文字，则两种方式都可以
   - 如果答案是代码，则应使用世界2（世界1会导致复制粘贴循环）
2. **你希望AI能够对这些内容进行操作吗？**
   - 是，那么就使用世界2
   - 否（敏感片段、不可信的代码、来自你不拥有的服务器的输出），则世界1更安全，因为工具不会连接到你的文件系统

### 开始启发式

| 如果工作是... | 使用... | 为什么 |
|---|---|---|
| 解释错误、解析日志、解释某些输出 | 任一世界 | 文字输出，无需编辑；选择哪个窗口打开即可 |
| 应该导致代码落地到文件中的任何内容 | 世界2 | 去掉了复制粘贴循环 |
| 可以用一句话描述的有针对性的更改 | 项目内聊天（世界2） | 快速、低开销，你阅读差异视图后再接受 |
| 多步工作，如跨文件更改、运行测试和修复循环或“探索项目并一致地进行更改” | 委托代理（世界2） | 模型拥有序列；你设定目标并审查最终状态 |
| 审查或思考你不希望AI执行的代码 | 世界1 | 工具可以读取但不能编辑 |
| 在设计决策之间权衡 | 任一世界 | 对话用户体验是关键 |

总结来说，记住这两件事：

**匹配模式到输出目标。** 如果答案应该“成为文件中的代码”，则使用能够放置这些代码的工具。如果答案应该是对话，则两种方式都可以。

**匹配模式到迭代速度。** 一次解释适合聊天。如果你需要对已知文件进行快速反馈循环，则使用项目内聊天，无需代理循环。对于你不想逐步监护的多步骤计划，请使用代理。

## 错误和日志

### 关键思想
错误、堆栈跟踪和日志输出正是Chat模型擅长解析的内容。一个Transformer的注意力机制就是为了在大量噪声中找到关键信息而设计的。使用它！

错误和日志是世界1的经典复制粘贴用例。关键是粘贴足够的上下文但不要过多，以及明确说明你正在尝试做什么。

### 关键目标
- 识别何时聊天模式适合处理错误或日志。
- 粘贴合适的上下文（既不多也不少）。
- 框定粘贴内容以便模型能够给出有用的答案而不是猜测。
- 将答案作为起点，而非绝对真理。

## 为什么聊天是正确的方式

典型的Python堆栈跟踪通常有10到40行噪声，其中一两行才是关键信息。一个500行的服务器日志可能只有三行真正重要。以下是Chat模型在这里有效的原因：

1. **输出是文字而不是代码在位。** 你正在寻找解释或至少是一个指针，而不是对文件进行编辑。聊天是更强的选择。
2. **输入是自包含的。** 你可以粘贴整个错误信息，而模型可以在不需要你的项目布局、历史记录或构建状态的情况下对其进行推理。

一个项目内聊天也可以很好地处理错误——并且往往是正确的工具，因为它可以查看抛出错误的文件而不必你手动粘贴它。对于长堆栈跟踪或不适合编辑器聊天面板的多页日志，或者当失败涉及不属于你的项目的服务器或系统输出时，web chat的空间扩展能力和自由复制粘贴的能力使其成为更好的选择。

### 应该粘贴什么

一个良好的实践是遵循以下三条简单的规则：

1. **粘贴整个相关块而不是最后一行**：Python堆栈跟踪的第一行（“文件X，在第Y行的foo中”）和最后一行（“ValueError: ...”）同样重要。大多数堆栈跟踪讲述了一个小故事：“程序是如何到达错误的路径。”模型需要这个路径，而不仅仅是目的地。

   **差：**
   ```
   ValueError: cannot convert string to float
   ```

   **更好：**
   ```
   Traceback (most recent call last):
     File "analyze.py", line 47, in <module>
       df["temp"] = df["temp"].astype(float)
     File ".../pandas/core/series.py", line 5816, in astype
       ...
   ValueError: could not convert string to float: 'N/A'
   ```

   第二个版本使原因（数据中的字符串`'N/A'`）显而易见。第一个则让模型猜测。

2. **仅在必要时进行剪裁**：你经常听到的建议是“粘贴前要大力剪裁”。实际上，现代聊天模型非常擅长在嘈杂的日志中找到关键的几行——这就是注意力机制的作用。对于典型的几百行日志，粘贴整个内容通常效果很好，并且剪裁带来的好处很小。

   剪裁值得付出努力的情况有三种：

   1. **日志足够大以至于接近上下文限制**（数万行或一个兆字节以上的文件）。这里你别无选择——使用`grep`、`tail`或你的编辑器来缩减它。
   2. **噪声是误导性的类型**——来自不同服务的无关红色`ERROR`行，看起来像是失败但其实不是的弃用警告，重复重试埋没了原始原因。模型有时会抓住最显眼的一行而不是实际的原因。
   3. **你希望更快、更便宜地周转**。输入越少意味着需要阅读的内容就越少，迭代速度也就越快。

   在这些情况之外，请不要过于纠结。如果你不知道哪个部分是相关的，则粘贴一个合理的片段并说明：“我认为失败发生在其中某个地方但我不确定要查看哪里。”模型会找到它。

3. **包括触发错误的命令或代码**：在真空环境中，模型可以分析堆栈跟踪，但它知道你正在运行什么将有很大帮助。即使是一句话也有帮助：

   > “我运行了`python analyze.py temperatures.csv`并得到了这个：”

   这个简短的前言可以让模型将错误与你执行的代码路径联系起来。

### 在粘贴周围说什么

一个有用的模式是三行简短的话加上粘贴内容：

> 你在做什么。
> 你期望发生什么。
> 实际发生了什么（带有粘贴的内容）。

例如：

> 我正在尝试将CSV文件中的炉温加载到DataFrame中并将温度列转换为浮点数。我期望转换能够成功。文件看起来很干净。相反，我得到了这个：
>
> ```
> Traceback ...
> ValueError: could not convert string to float: 'N/A'
> ```

这足以让模型找到正确的答案（某些行有`'N/A'`字符串）并建议正确的修复方法（明确处理缺失值）。

如果你已经尝试过一些事情，说清楚。"我尝试了`pd.read_csv(..., na_values='N/A')`但没有改变错误。" 这样可以节省模型从你已排除的可能性中进行猜测的时间。

### 如何使用答案

模型对错误的第一个回答往往是*可能但不准确的根因*。它会识别出正确的区域（“你的列中有非数字值”），但在特定行或适用于你情况的具体修复方面可能会猜错。将答案视为**搜索查询**，而不是确定的结果：

- 诊断是否与你在数据或代码中看到的一致？
- 建议的修复是否可以快速验证（一行、一个测试）？
- 如果建议的修复不起作用，请在下一轮中说明并粘贴新的输出。
